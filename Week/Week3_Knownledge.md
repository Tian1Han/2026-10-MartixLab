## 🔍 一、通用强化学习 Demo 分析方法

分析任何强化学习 Demo，第一步绝不是逐行读代码，而是从宏观上拆解以下核心要素与工程架构。

### 1. 强化学习核心要素分解
- **场景 (Scene)**：定义环境与 Agent（机器人）的物理存在。
- **观测 (Observation)**：策略的输入，代表 Agent 从场景中“看到”的信息集合（即观测空间）。
- **动作 (Action)**：策略的输出，代表 Agent 对场景施加的影响（即动作空间）。
- **奖励 (Reward)**：环境给 Agent 的即时反馈，引导其向目标学习。
- **状态流转边界**：
  - **初始状态**：任务从何开始（包含初始化的参数与随机范围）。
  - **终止状态 (Terminated)**：任务因**失败**而提前结束。
  - **截断状态 (Truncated)**：任务因**超时**（达到最大步数）而强制结束。
  - *(注：成功状态通常不触发 Terminated，而是持续获取奖励直至 Truncated)*
- **域随机化 (Domain Randomization)**：在 reset 时对初始状态、环境参数等注入随机噪声，以增强策略的鲁棒性。

### 2. 深入代码的通用流转与接口规范
在终端中探索环境的常用命令：
- `view.py`：环境纯物理预览。
- `train.py`（搭配 `--render`）：启动训练并开启可视化。
- `tensorboard`：查看训练曲线分析瓶颈。
- `play.py`：加载 Checkpoint 进行推理测试。

**框架底层接口规范**：
- 框架结构分为 `motrix_envs`（任务环境侧）和 `motrix_rl`（RL 算法侧）。
- **`NpEnv` (底层接口)**：开发者必须实现 `apply_action()`、`update_state()`、`reset()` 三个抽象方法。
- **`NpWrapper` (顶层封装)**：对外提供强化学习标准的 `reset()` 和 `step()` 接口，内部封装并调用了 `NpEnv` 的单步交互与重置逻辑。

## 🛒 二、CartPole 任务深度剖析与实操

### 1. 任务目标与交互流程
- **任务目标**：让小车留在轨道中央附近（位置 $x$ 接近 0），保持摆杆竖直（角度 $\theta$ 接近 0），尽可能久地不越界（存活越久，累计奖励越高）。
- **标准交互闭环**：
  > `reset()` 返回初始观测 $S_0$ → 策略网络输出动作 $A_t$ → `env.step(A_t)` → 仿真底层推进 → 产生新观测 $S_{t+1}$ 与奖励 $R_t$ → 判断是否结束（若未结束，进入下一帧循环；若结束，调用 `reset_done_envs()` 重新采样状态）。

### 2. CartPole 八要素核心数据速查表

| 分析要素                    | CartPole 具体设定                                            |
| :-------------------------- | :----------------------------------------------------------- |
| **🤖 智能体执行器**          | 小车的 slider 滑动关节及对应的 slide 电机                    |
| **👁️ 观测 (Obs)**            | 4 维连续量：`[x, theta, x_dot, theta_dot]` (位置与速度拼接)  |
| **💪 动作 (Action)**         | 1 维连续量，输出范围为 `[-3.0, 3.0]`                         |
| **🎯 奖励 (Reward)**         | 纯存活奖励：每一步未触发结束即获得 `1.0` 分。最高可得约 1000 分。 |
| **🏁 初始状态**              | 默认关节初值为 0，重置时叠加 $U(-0.01, 0.01)$ 的均匀分布噪声。 |
| **❌ 失败条件 (Terminated)** | 1. 杆角度绝对值 $> 0.2$ rad (含 NaN)。<br>2. 小车位置 $< -0.8$ m 或 $> 0.8$ m。<br>*(注：严格大于/小于才触发边界)* |
| **⏱️ 超时截断 (Truncated)**  | 设定 `max_episode_steps = 1000` (最长 10s，控制步长 0.01s)。 |
| **🎲 域随机化**              | （本基础任务中主要体现在初始状态的随机噪声扰动上）           |

### 3. 代码底层实现细节透视
阅读 `xxx_env.py` 时，需要重点关注数据是如何在代码与物理引擎间流转的：

- **动作执行链路**：
  - 代码层面：`apply_action()` 中没有做额外的裁剪或缩放，直接将策略输出写入 `state.data.actuator_ctrls`。
  - 物理层面：引擎交给 XML 定义中的 `slide` 电机驱动关节。
  - **缩放奥秘**：由于 XML 配置了 `ctrllimited="true"` 和 `gear="100"`，控制输入实际上被放大了 100 倍转为广义力（最大控制力约 $3.0 \times 100 = 300$ N）。
- **观测提取逻辑**：
  - 提取代码：`obs = np.concatenate([dof_pos, dof_vel], axis=-1)`，极其直观地拼装了 4 维状态。
- **终止判定逻辑**：
  - 提取代码：利用 `np.logical_or` 级联判断角度超限、位置超限和 NaN 异常。
- **重置 (Reset) 逻辑**：
  - 发生时机：在 `NpEnv.step()` 的末尾，框架会判断 `done = terminated OR truncated`。
  - 运作机制：一旦发现有环境结束，立即调用内部的 `_reset_done_envs()`，进而触发子类自定义的 `reset()` 进行新一轮的状态采样初始化。

## 🌟 三、本周核心知识主线总结

1. **宏观与微观结合**：看 Demo 不能直接啃代码，必须先用“八要素”给任务画出整体蓝图。
2. **理解动作映射的 Gap**：策略输出的 Action 数值，往往需要结合 XML 模型配置（如 `gear` 传动比）才能换算为真实的物理力/力矩。
3. **Terminated 与 Truncated 的严格区分**：前者是“做错了被判负”，后者是“时间到了被重置”。在 CartPole 中，由于纯靠“存活”拿分，避免被 Terminated 就是模型优化的唯一方向。
